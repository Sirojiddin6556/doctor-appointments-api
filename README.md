# API записи пациентов в клинику

REST API для записи пациентов к врачам. Врач публикует свободные временные
слоты, пациент выбирает слот и может отменить запись, а администратор получает
общий список записей с фильтрами.

Проект построен на Python 3.11, Django 5.2, Django REST Framework и PostgreSQL
16. Все основные бизнес-правила дополнены ограничениями базы данных и
проверяются автоматическими тестами.

## Архитектура

Приложение разделено на независимые Django-приложения:

- `users` — пользователь, роли, регистрация и JWT-аутентификация;
- `doctors` — профиль врача, фильтрация врачей и поиск свободных слотов;
- `slots` — создание расписания врача пакетами и его просмотр;
- `appointments` — бронирование, отмена и административный список записей;
- `common` — общие классы разрешений и тестовые помощники.

Внешний HTTP-запрос проходит через маршруты Django, затем DRF вызывает viewset.
Viewset проверяет роль, сериализатор проверяет формат данных, сервисная логика
выполняется внутри транзакции, а PostgreSQL окончательно гарантирует целостность.
Временные значения принимаются в ISO 8601 и хранятся в UTC.

## Быстрый запуск

Требуются Docker Desktop и Docker Compose.

```bash
git clone <адрес-репозитория>
cd testovoe-zadaniye
docker compose up --build
```

После запуска доступны:

- API: <http://localhost:8000/api/>;
- Swagger UI: <http://localhost:8000/api/docs/>;
- Django Admin: <http://localhost:8000/admin/>.

Compose сам создаёт PostgreSQL, ждёт его готовности, применяет миграции,
собирает статику, **наполняет базу демо-данными** (`seed_demo_data`,
идемпотентно; отключается `SEED_DEMO_DATA=false`) и запускает сервер. Файл
`.env` для первого запуска не требуется — значения по умолчанию заданы в
`docker-compose.yml`.

По умолчанию контейнер стартует с `DJANGO_DEBUG=False` (статику отдаёт
WhiteNoise, поведение близко к боевому). Для трейсбеков при отладке:
`DJANGO_DEBUG=True docker compose up`.

Демо-аккаунты (пароль у всех `DemoPass123!`): `admin_demo`, `dr_cardio`,
`dr_neuro`, `dr_derma`, `patient_demo1..3`.

## Подробный процесс запуска

1. Docker Compose создаёт контейнер `db` на основе PostgreSQL 16 Alpine.
2. База получает имя, пользователя и пароль из `.env` либо из значений по
   умолчанию. Данные сохраняются в volume `postgres_data`.
3. Healthcheck выполняет `pg_isready`, поэтому API запускается только после
   готовности базы.
4. Образ API устанавливает зависимости из `requirements.txt`.
5. `docker/entrypoint.sh` ждёт доступности PostgreSQL, запускает
   `python manage.py migrate`, а затем передаёт управление серверу.
6. Django загружает настройки, подключает приложения, JWT, фильтры, Swagger и
   русское логирование.
7. Логи приложений выводятся в консоль контейнера. Их можно смотреть командой
   `docker compose logs -f api`.
8. Для остановки без удаления данных используется `docker compose down`.
   Команда `docker compose down -v` дополнительно удалит базу и volume.

Для локального запуска без Docker нужно создать виртуальное окружение,
установить зависимости и использовать PostgreSQL:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

SQLite не поддерживается: ограничения пересечений используют PostgreSQL
`ExclusionConstraint` и расширение `btree_gist`.

## API

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/auth/register/` | любой | регистрация пациента (email обязателен и уникален) |
| `POST /api/auth/login/` | любой | получение access и refresh JWT |
| `POST /api/auth/refresh/` | любой | обновление access-токена (с ротацией) |
| `POST /api/auth/logout/` | авторизованный | отзыв refresh-токена (blacklist) |
| `GET /api/doctors/` | авторизованный | список врачей; `?specialization=`, `?branch=` (точное, без регистра), `?search=` (имя/специализация), `?page`, `?page_size` |
| `GET /api/doctors/{id}/slots/?date=YYYY-MM-DD` | авторизованный | свободные и ещё не прошедшие слоты врача за дату (сутки в UTC) |
| `POST /api/appointments/` | пациент | бронирование слота |
| `GET /api/appointments/` | пациент | собственные записи; `?status=booked,cancelled,completed` |
| `POST /api/appointments/{id}/cancel/` | пациент | отмена собственной записи |
| `POST /api/slots/` | врач | пакетное создание слотов |
| `GET /api/slots/mine/` | врач | собственное расписание |
| `GET /api/admin/appointments/` | администратор | все записи; `?doctor=`, `?branch=`, `?status=`, `?date_from=`, `?date_to=` |
| `POST /api/admin/appointments/{id}/cancel/` | администратор | принудительная отмена (без окна «за 2 часа») |
| `GET·POST /api/admin/doctors/` | администратор | список врачей / создание учётной записи врача (пользователь + профиль) |
| `GET·PATCH·DELETE /api/admin/doctors/{id}/` | администратор | карточка / правка специализации, филиала, ФИО, активности / удаление |
| `GET /api/admin/users/` | администратор | все пользователи; `?role=`, `?search=` |
| `GET /api/docs/` | любой | Swagger UI |
| `GET /healthz/` | любой | liveness/readiness (проверяет БД) |

Для защищённых endpoint передавайте заголовок:

```text
Authorization: Bearer <access-токен>
```

Пример бронирования:

```json
{"slot": 12}
```

Пример пакетного создания слотов:

```json
{
  "start_time": "2026-09-07T09:00:00Z",
  "end_time": "2026-09-07T13:00:00Z",
  "slot_duration_minutes": 30
}
```

## Веб-интерфейс

На `/` отдаётся SPA (`templates/frontend`, `static/frontend`) — тонкий клиент
над тем же REST API, для ручной проверки без Postman. Вкладки зависят от роли
из JWT:

- **пациент** — каталог врачей (поиск, фильтры), свободные слоты, свои записи,
  отмена;
- **врач** — своё расписание (с пометкой, кто занял слот) и пакетное создание
  слотов на день;
- **админ** — консоль из трёх разделов: «Записи» (все записи, фильтры,
  принудительная отмена), «Врачи» (список + создание/правка/удаление учётных
  записей врачей), «Пользователи» (все аккаунты, фильтр по роли). То же, что в
  Django admin, но через API.

Весь вывод экранируется, страница отдаётся со строгим `Content-Security-Policy`.
По ТЗ фронтенд не оценивается — это вспомогательный инструмент, вся логика и
проверки на стороне API.

## Демонстрационные данные

```bash
docker compose exec api python manage.py seed_demo_data
```

Команда создаёт трёх врачей, трёх пациентов, администратора и по восемь
получасовых слотов каждому врачу. Все демонстрационные аккаунты используют
пароль `DemoPass123!`:

`admin_demo`, `dr_cardio`, `dr_neuro`, `dr_derma`, `patient_demo1`,
`patient_demo2`, `patient_demo3`.

Повторный запуск безопасен: существующие пользователи пропускаются, а слоты
за уже заполненный день не дублируются.

## Тестирование

В Docker:

```bash
docker compose exec api python manage.py test apps --noinput -v 2
```

Проверка конфигурации:

```bash
docker compose exec api python manage.py check
```

65 тестов покрывают регистрацию (в т.ч. обязательность и уникальность email),
JWT (login, refresh, logout с blacklist), фильтрацию и поиск врачей,
пагинацию с `page_size`, UTC, разрешения (роль + queryset + объект),
отмену и повторное освобождение слота (правило 5), фильтр по статусу,
админские фильтры и админ-консоль (создание/правка/удаление врача,
принудительная отмена, список пользователей), отсутствие пересечений,
конкурентное бронирование и защиту от N+1.

Тест конкурентного бронирования (правило 1) запускает десять реальных
параллельных потоков против живой БД: ровно один запрос возвращает `201`,
остальные — чистый `400`, ни одного `500`; в БД остаётся одна `booked`-запись.

CI (`.github/workflows/tests.yml`) дополнительно прогоняет
`manage.py check --deploy` на профиле `DEBUG=False`.

## Бизнес-правила и защита данных

1. Один слот нельзя забронировать дважды: `select_for_update()` плюс частичный
   `UniqueConstraint` для активных записей.
2. Нельзя бронировать слот, который уже начался: проверка времени в API.
3. У пациента не может быть двух пересекающихся активных записей:
   прикладная проверка плюс PostgreSQL `ExclusionConstraint`.
4. Отмена разрешена только более чем за два часа до начала.
5. После отмены слот снова свободен: свободность вычисляется по отсутствию
   записи со статусом `booked`, отдельный флаг не хранится.
6. Пациент и врач видят только собственные объекты. Проверяются и роль, и
   queryset, и объектное разрешение.
7. Один врач не может создать пересекающиеся слоты. Ограничение действует и
   при параллельных запросах.
8. Даты хранятся и возвращаются в UTC, вход поддерживает ISO 8601 с часовым
   поясом.

Жизненный цикл записи: `booked` → `cancelled` (отмена пациентом) или
`completed`. Отдельного endpoint'а для завершения нет: приём считается
состоявшимся по факту `end_time < now`, если не был отменён. Перевод делает
команда `python manage.py close_past_appointments` (рассчитана на запуск по
расписанию, например раз в 10 минут).

## Принятые допущения

ТЗ намеренно оставляет часть решений на исполнителя. Приняты следующие:

- **Роли.** Саморегистрация — только пациент; открывать выбор роли в `register`
  нельзя — любой объявил бы себя врачом. Врачей заводит администратор через
  `POST /api/admin/doctors/` (пользователь + профиль одним запросом) или в
  админ-консоли фронта; админы — через `seed_demo_data` / Django admin.
  Профиль врача (`specialization`, `branch`) создаётся вместе с учёткой; если
  роль `doctor` есть, а профиля нет — эндпоинты врача отвечают `403`, не `500`.
- **email.** Для пациента обязателен и уникален (единственный контакт и ключ
  восстановления). Учётки из seed/admin этим правилом не ограничены.
- **Конфликты брони.** Проигравший гонку за слот получает `400` с понятным
  текстом (не `409`): для клиента это ошибка валидации «слот занят», а не
  специальная семантика конфликта; формат тела — стандартный DRF
  (`{"поле": ["сообщение"]}` либо `{"detail": "..."}`).
- **Коды успеха.** Бронирование и создание слотов — `201`; отмена — `200` с
  телом записи; logout — `205`.
- **`?date=` в свободных слотах** трактуется как календарные сутки в **UTC**.
  Прошедшие слоты сегодняшнего дня в выдачу не попадают (их всё равно нельзя
  забронировать по правилу 2).
- **Пересечения** считаются по полуинтервалу `[start, end)`: смежные слоты
  (`end == start`) допустимы. Пересечение записей пациента проверяется по
  всем врачам, слотов врача — по всем филиалам (врач физически один).
- **JWT.** Access 15 мин, refresh 7 дней, refresh ротируется и после ротации
  или `logout` попадает в blacklist. Токены на клиенте — в `localStorage`
  ради простоты демо; в проде их место в `HttpOnly`-cookie. От выноса
  украденного токена на чужой домен защищает строгий `Content-Security-Policy`
  (`connect-src 'self'`), а весь вывод фронта экранируется.
- **Production-профиль.** При `DJANGO_DEBUG=False` автоматически включаются
  `SECURE_*`, `SESSION/CSRF_COOKIE_SECURE`, HSTS (см. `config/settings.py`).
  В `docker-compose.yml` HTTPS-редирект и HSTS выключены — стенд локальный по
  HTTP. `.env.example` содержит боевые значения.
- **Что сознательно не делалось** (вне объёма 2-дневного API-задания):
  уведомления (email/SMS/push), rate limiting бронирования/отмены (слот
  защищён правилом 1), пер-филиальные таймзоны и календарь праздников,
  редактирование/перенос слотов, `Idempotency-Key`, аудит-лог, бэкапы БД.

## Логирование

Настройка `LOGGING` находится в `config/settings.py`. Для приложения `apps`
используется формат:

```text
дата и время | уровень | модуль | сообщение
```

Русские записи создаются при регистрации, бронировании, отмене, создании и
просмотре расписания, выдаче свободных слотов, ошибках ограничений БД и
заполнении демонстрационными данными. Уровень можно изменить через `LOG_LEVEL`.
В Docker логи доступны через `docker compose logs -f api`.

## Что можно улучшить

- перенести JWT в `HttpOnly`-cookie вместо `localStorage`;
- добавить редактирование, удаление и перенос ещё не занятых слотов;
- добавить `Idempotency-Key` для повторных запросов бронирования;
- расширить профиль врача и пациента;
- добавить request id и структурированные JSON-логи для production;
- добавить throttling для бронирования и отмены, а не только для входа;
- заменить cron-команду `close_past_appointments` на очередь задач.
